CríticaH-01 Seguridad

Un cliente puede consultar los envíos de otro cliente cambiando el idClient de la petición

La API toma el idClient del query string y filtra con él. Para el rol CLIENT no lo compara con el usuario del token: el ClientAccessResolver devuelve una lista vacía sin validar y la lectura de los claims del usuario está comentada. Afecta a myshipments (allshipments, filterShipments, allhistory, filterhistory, detailsshipments), home (totals, filters) y reports/home. El API Gateway no reescribe el parámetro.

Estado: Detectado en el código. Se espera que 318 y 365 FALLEN al ejecutarlos.

Recomendación: Tomar el documento del cliente desde el token (claim) en el backend y rechazar (403) cualquier idClient distinto.

Evidencia: Connection360.Api/Controllers/MyShipmentsController.cs:44-57; Connection360.Application/UseCases/GetMyShipmentsUseCase.cs:43-50; Connection360.Application/Services/ClientAccessResolver.cs:26-27; Connection360.Api/Controllers/HomeController.cs:105-111 (comentado); Connection360.ApiGateway/appsettings.json (ReverseProxy: solo agrega X-Forwarded-By)

MediaH-05 Seguridad

El API Gateway tiene credenciales escritas en el código y emite tokens con el mismo emisor que Auth0

TokenEndpoints define tres clientes (admin-client, editor-client, reader-client) con sus secretos en el código y firma tokens con el mismo Issuer y Audience que usa Auth0. La API valida la firma con las llaves de Auth0 (Authority), así que lo más probable es que rechace esos tokens, pero hay que confirmarlo.

Estado: Por confirmar con el TC384 (manual).

Recomendación: Sacar los secretos del código (User Secrets o Key Vault) y usar un emisor propio para los tokens del Gateway.
