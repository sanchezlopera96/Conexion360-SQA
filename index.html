Hallazgos de la revisión (14, 3 críticos)

Revisión estática del código (Conexion360_front, Connection360ApiCore) y de los test cases de Azure DevOps. No proviene de ejecuciones. (2026-10-17)
CríticaH-01 Seguridad

Un cliente puede consultar los envíos de otro cliente cambiando el idClient de la petición

La API toma el idClient del query string y filtra con él. Para el rol CLIENT no lo compara con el usuario del token: el ClientAccessResolver devuelve una lista vacía sin validar y la lectura de los claims del usuario está comentada. Afecta a myshipments (allshipments, filterShipments, allhistory, filterhistory, detailsshipments), home (totals, filters) y reports/home. El API Gateway no reescribe el parámetro.

Estado: Detectado en el código. Se espera que 318 y 365 FALLEN al ejecutarlos.

Recomendación: Tomar el documento del cliente desde el token (claim) en el backend y rechazar (403) cualquier idClient distinto.

Evidencia: Connection360.Api/Controllers/MyShipmentsController.cs:44-57; Connection360.Application/UseCases/GetMyShipmentsUseCase.cs:43-50; Connection360.Application/Services/ClientAccessResolver.cs:26-27; Connection360.Api/Controllers/HomeController.cs:105-111 (comentado); Connection360.ApiGateway/appsettings.json (ReverseProxy: solo agrega X-Forwarded-By)

Casos de Azure: 318, 357, 365

AltaH-02 Seguridad

Un analista puede ver los clientes asignados a otro colaborador

Para ANALISTAOPE y ANALISTASAC, los clientes permitidos se buscan con el idClient recibido en la URL (GetCustomersByCollaboratorAsync(request.IdClient)). Si el analista envía el documento de otro colaborador, obtiene los clientes de ese colaborador.

Estado: Detectado en el código. El TC359 solo valida la interfaz y no lo detecta; falta un caso de API.

Recomendación: Igual que H-01: identificar al colaborador por el token. Agregar en Azure un caso de API para analistas.

Evidencia: Connection360.Application/Services/ClientAccessResolver.cs:26-46

Casos de Azure: 359

CríticaH-03 Seguridad

Cuatro servicios sin autenticación permiten crear datos

GET /settings/createcustomerdb, GET /settings/createcollaboratordb, GET /settings/createcustomercollaboratordb y POST /settings/generatenotificationOutboxTest están marcados con [AllowAnonymous]. Los tres GET crean registros en la base de datos, y el POST genera eventos de notificación.

Estado: Detectado en el código. El TC378 FALLARÁ y, al ejecutarlo, creará los NIT de prueba 999000111 y 999000112: no correrlo en el ambiente compartido hasta corregir.

Recomendación: Quitar [AllowAnonymous] (o retirar los servicios de prueba del despliegue) y no crear datos con métodos GET.

Evidencia: Connection360.Api/Controllers/SettingsController.cs:276-325

Casos de Azure: 378

MediaH-05 Seguridad

El API Gateway tiene credenciales escritas en el código y emite tokens con el mismo emisor que Auth0

TokenEndpoints define tres clientes (admin-client, editor-client, reader-client) con sus secretos en el código y firma tokens con el mismo Issuer y Audience que usa Auth0. La API valida la firma con las llaves de Auth0 (Authority), así que lo más probable es que rechace esos tokens, pero hay que confirmarlo.

Estado: Por confirmar con el TC384 (manual).

Recomendación: Sacar los secretos del código (User Secrets o Key Vault) y usar un emisor propio para los tokens del Gateway.

Evidencia: Connection360.ApiGateway/Endpoints/TokenEndpoints.cs:42-55; Connection360.ApiGateway/appsettings.json:10-11; Connection360.Api/Extensions/ServiceCollectionExtensions.cs:120-130

Casos de Azure: 384

MediaH-13 Datos

Fechas logísticas incoherentes: llegada y entrega anteriores a la salida

HBL-4XJ4A3S8 (Éxito, En tránsito) tiene ETD 03/09/2025, ATD 03/10/2025 y ETA 03/11/2025, pero ATA 14/03/2025 y bodega destino, nacionalización, despacho, planilla y entrega de contenedor entre el 14 y el 21/03/2025, es decir, antes de salir. Una guía En tránsito no debería tener ATA. El listado y el detalle traen las mismas fechas; solo cambia el formato (03/09/2025 frente a '03 sept 2025').

Estado: Confirmado en la API el 21-oct.

Recomendación: Validar en el ETL el orden de las fechas logísticas (ETD <= ATD <= ATA y ETA) y que ATA esté vacía mientras la guía no haya llegado. Opcional: usar el mismo formato de fecha en el listado y el detalle.

Evidencia: API detailsshipments y allshipments del 21-oct (resultados/datos_ambiente.json, solo local). El TC340 falló al principio por el formato distinto; se corrigió el script.

BajaH-14 Funcional

Una guía inexistente no muestra 'Envío no encontrado'

Al abrir por URL el detalle de una guía que no existe (ZZ-0000000), no aparece 'Envío no encontrado'. El front muestra ese mensaje solo cuando la API responde bien y sin datos; si la API responde con error, muestra 'No fue posible cargar el detalle'.

Estado: Confirmado en la API el 21-oct.

Recomendación: Que el servicio de detalle responda 200 sin datos (o 404 tratado como no encontrado) para una guía inexistente.

Evidencia: TC325, Reports/20261021_203118. La API detailsshipments responde 400 'No hay información para la solicitud' para ZZ-0000000 (21-oct). Conexion360_front: shipment-detail.ts trata cualquier error como 'No fue posible cargar el detalle'.
